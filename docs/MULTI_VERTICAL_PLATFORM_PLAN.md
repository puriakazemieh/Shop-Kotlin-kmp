## ۰) خلاصه‌ی حسابرسیِ ۵ دیزاین

هر ۵ اکسپورت روی **همان معماریِ فروشگاهیِ کارمیلا** ساخته شده‌اند (۱۶ صفحه‌ی مشترک: خانه، دسته‌بندی،
محصول، سبد، تسویه، جستجو، پروفایل، علاقه‌مندی، سفارش‌ها، جزئیاتِ سفارش، آدرس‌ها، کیف پول، بلاگ،
جزئیاتِ بلاگ، ادیتورِ بلاگ، ورود/ثبت‌نام) + پنلِ ادمینِ مشترک (داشبورد/محصولات/واریانت/سفارش/محتوا/مالی).
این بخشِ مشترک **از قبل در کدبیس پیاده‌سازی شده** (سندِ قبلی). چیزی که تازه است:

| اپ | عمودیِ اضافه | فیلدهای دادهٔ اختصاصی | صفحاتِ اضافه |
|---|---|---|---|
| **Fashion-Karmila** (پوشاک) | هیچ‌کدام — برندِ پایه (Carmila) | — | — |
| **Watch-TTBol** (ساعت) | هیچ‌کدام، فقط اسکیمای محصولِ متفاوت | `movement, caseSize, caseMat, waterRes, glass, strap, warranty` | — |
| **Perfume-AminSmell** (عطر) | هیچ‌کدام، فقط اسکیمای محصولِ متفاوت | `gender, conc, family, notesTop[], notesHeart[], notesBase[], longev, sillage, country, vol` | — |
| **Academy-Kazemieh** (آموزشگاه) | آموزشگاه (دوره/سمینار/کارگاه) | `courseType, format, isOnline, level, sessions, duration, cert, location, capacity, syllabus[], jobMarket, projectBased, freeUpdate, instructorBio, instructorSkills[]` | دوره‌های من، پخش‌کننده، آزمون، گواهی + ادمین: محصولات‌آموزشی، درخواست‌های دوره |
| **Psych-Mehrjoo** (مشاوره) | آموزشگاه + نوبت‌دهی + تست روان‌شناسی | خدمت: `specialty, format, duration, approach`؛ نوبت: `appts[]{patient, service, date, time, dur, mode, status}`؛ تست: `tests[]{title, price, resultMode, questions[], ranges[]}` | همان صفحاتِ آموزشگاه + فروشگاهِ تست + انجامِ تست + ادمین: نوبت‌دهی، تست‌ساز |

**نتیجه‌ی مهم:** «آموزشگاه» و «مشاوره» **از قبل به‌عنوانِ عمودی‌های کاملِ کاربر+ادمین در کدبیس هست**
(`feature:academy`, `feature:clinic`, `feature:admin:academy`, `feature:admin:clinic`). کاری که تا امروز
نبود و این سند اضافه می‌کند:
1. **داینامیک‌بودنِ روشن/خاموشیِ عمودی‌ها per برند** (✅ الان انجام شد — فازِ ۰).
2. **تفکیکِ نوعِ فعالیت** (دوره/سمینار/کارگاه) و **شکلِ برگزاری** (آنلاینِ ضبط‌شده/زنده/حضوری/آفلاین)
   داخلِ عمودیِ آموزشگاه — الان هر دوره فقط بولینِ ساده `duration`/بدونِ فرمت دارد.
3. **عمودیِ کاملاً جدید: تست‌های روان‌شناسیِ قابل‌خرید** (وجود ندارد، باید از صفر ساخته شود).
4. **پالایشِ پنلِ ادمینِ نوبت‌دهی** (ساعاتِ کاری/مدتِ نوبت/پروندهٔ مراجع).
5. **مقایسه‌ی محصول** (فیچرِ جنریکِ فروشگاهی، مستقل از عمودی‌ها).
6. **اسپک‌کارتِ محصولِ per دسته** برای ساعت/عطر (رندرِ فیلدهای فنی/رایحه در صفحه‌ی محصول).

## ۱) معماریِ عمودی‌های داینامیک (پایه‌ی همه‌ی فازهای بعدی)

### چه چیزی همین الان اضافه شد (فازِ ۰)
- `core/designSystem/brand/Brand.kt`: `BrandFeatures` چهار پرچمِ جدید گرفت:
  `academy`, `clinic`, `psychTests`, `productComparison` (پیش‌فرض `false`).
- دو برندِ جدید: `AcademyBrand` (`academy=true`) و `PsychBrand` (`academy=true, clinic=true, psychTests=true`).
- `MoreScreen.kt` پارامترهای `showAcademy`/`showClinic` گرفت؛ ردیف‌های «دوره‌های من»، «نوبت‌های من»،
  «دوره‌های آموزشی»، «مشاوره و روان‌شناسی» فقط وقتی برند آن عمودی را روشن کرده نمایش داده می‌شوند.
- `AdminPanelScreen.kt` تب‌های «آموزشگاه»/«مشاوره» را فقط وقتی `brand.features.academy/clinic` باشد
  به لیستِ تب‌ها اضافه می‌کند (`buildList` + ایندکسِ داینامیک به‌جای عددِ ثابت).
- `composeApp/build.gradle.kts`: دو فلِیورِ جدید `academy` و `psych` (هم‌الگو با `atris`/`chronos`).

### الگو برای عمودیِ بعدی (مثلاً «تست روان‌شناسی»)
هر عمودیِ جدید همین ۴ قدم را تکرار می‌کند:
1. یک پرچمِ جدید در `BrandFeatures` (مثلاً از قبل `psychTests` رزرو شده).
2. ماژول‌های Gradleِ مستقل: `feature:psychtest` (کاربر) + `feature:admin:psychtest` (ادمین) —
   دقیقاً هم‌ساختار با `feature:clinic`/`feature:admin:clinic`.
3. رجیستریِ Koinِ مشروط: چون ماژول‌های Koin فقط تعریفِ DI هستند (بارِ اجراییِ صفر)، همیشه در
   `App.kt` ثبت می‌شوند؛ آنچه واقعاً مشروط است فقط **نمایشِ UI** (ردیفِ nav / تبِ ادمین) است —
   دقیقاً همان الگویی که در فازِ ۰ برای academy/clinic پیاده شد.
4. ردیفِ nav در `MoreScreen` + تبِ ادمین در `AdminPanelScreen`، هر دو پشتِ پرچمِ برند.

> **چرا این‌طور و نه حذفِ فیزیکیِ ماژول از build؟** چون همه‌ی ۵ اپ از یک artifact (یا حداقل یک
> کدبیسِ مشترک) خروجی می‌گیرند؛ حذفِ کاملِ ماژول از گراف کامپایل نیاز به build variant/source-set
> جدا برای هر برند دارد که پیچیدگیِ Gradleِ غیرضروری اضافه می‌کند. مخفی‌کردنِ UI + غیرفعال‌بودنِ
> endpointهای سرور (چون سرور هم per دیتابیس/دیپلویِ جدا per برند اجرا می‌شود) برای وایت‌لیبل کافی است.

## ۲) عمودیِ آموزشگاه: تفکیکِ دوره/سمینار/کارگاه + آنلاین/حضوری

### مدلِ سرور (جدید — نیاز به migration)
`CourseEntity` فعلاً `title, slug, price, sections[]` دارد. اضافه می‌شود:

```
courseType   enum(COURSE, SEMINAR, WORKSHOP)      -- دوره / سمینار / کارگاه
format       enum(ONLINE_RECORDED, ONLINE_LIVE, IN_PERSON, OFFLINE)
level        enum(BEGINNER, INTERMEDIATE, ADVANCED)   nullable
location     varchar   nullable   -- فقط IN_PERSON
capacity     int       nullable   -- فقط IN_PERSON (ظرفیتِ کلاس)
seatsTaken   int default 0        -- فقط IN_PERSON (برای رزروِ ظرفیت)
jobMarketBadge   boolean default false   -- نشانِ «پل ورود به بازار کار»
freeUpdateBadge  boolean default false   -- نشانِ «بروزرسانی رایگان»
instructorBio    text      nullable
instructorSkills text[]    nullable  (یا jsonb مثلِ attributes محصول)
```

- migration: `db/init/025_add_course_type_format.sql`.
- منطق: اگر `format == IN_PERSON` یا `OFFLINE` → دورهٔ سفارشی‌مانند (فروش=رزروِ صندلی، بدونِ
  پخش/پیشرفت). ثبت‌نام وقتی `seatsTaken >= capacity` باید با `ConflictException` رد شود (شبیهِ
  الگوی قفلِ pessimistic که در `AvailabilitySlotRepository` برای نوبت‌دهی هست — همان الگو برای
  `CourseEntity.seatsTaken` هم لازم است).
- اگر `format == ONLINE_*` → مسیرِ فعلیِ enroll+progress دست‌نخورده می‌ماند.

### مدلِ کلاینت
- `domain/academy/Academy.kt`: `CourseSummary`/`CourseDetail` فیلدهای بالا را می‌گیرند.
- `AdminAcademyScreen.kt`: فرمِ «افزودن دوره» یک `Dropdown`/`SegmentedButton` برای `courseType` و
  `format` می‌گیرد؛ وقتی `format` حضوری/آفلاین است دو فیلدِ `location`/`capacity` نمایش داده می‌شوند
  (وگرنه مخفی).
- `CourseDetailScreen.kt` (کلاینت): اگر `format` حضوری/آفلاین → کارتِ «مکان و ظرفیت» به‌جای دکمهٔ
  «ادامه/پخش»؛ CTA می‌شود «رزروِ صندلی» (هنوز از مسیرِ خرید/enroll فعلی رد می‌شود، فقط UI فرق دارد).
- پخش‌کننده (`CoursePlayerScreen` — هنوز ساخته نشده، بخشِ بعدی): فقط برای `format` آنلاین ظاهر می‌شود.

### پخش‌کننده‌ی ویدیو + کیفیت + آفلاین + آزمون + گواهی (فقط دوره‌های آنلاین)
این بخش در دیزاین (`18-player.html`, `19-quiz.html`, `20-cert.html`) هست ولی در کدِ فعلی، `feature:academy`
فقط enroll+progress دارد؛ پخش/آزمون/گواهی هنوز نیست. پیشنهاد:

- **پخش با انتخابِ کیفیت:** هر `LessonEntity` به‌جای یک `videoUrl` ساده، `videoVariants: jsonb`
  (`[{quality:"720p", url:"..."}]`) نگه دارد. کلاینت یک `DropdownMenu` کیفیت روی پلیرِ ویدیوی
  موجود (بررسی کن از چه کتابخانه‌ای برای ویدیو استفاده شده؛ اگر Media3/ExoPlayer است فقط منبعِ URL
  عوض می‌شود). **توجه امنیتی:** اگر ویدیوها باید ضدِ دانلود/DRM باشند (HLS با توکنِ کوتاه‌مدت)،
  این یک تصمیمِ زیرساختی جدا از دامنه است — در HANDOFF هم به‌عنوانِ «سرویسِ ویدیوی واقعی» به بعد
  موکول شده؛ برای MVP همان لینکِ مستقیم با چند کیفیت کافی است.
- **ذخیره‌ی آفلاین:** فقط در پلتفرم‌هایی با فایل‌سیستمِ محلی (اندروید/دسکتاپ) معنی دارد؛ روی
  وب/iOS از طریق `expect/actual` در `core:common` یک `VideoDownloadManager` تعریف کن که در وب
  no-op باشد.
- **آزمونِ پایانِ دوره:** `QuizEntity{courseId, questions:jsonb, passScore}` + `QuizAttemptEntity`؛
  اگر `attempt.score >= passScore` → صدورِ گواهی.
- **گواهیِ دوزبانه:** `CertificateEntity{userId, courseId, issuedAt, certNumber}` + رندرِ PDF سمتِ
  سرور (کتابخانه‌ای مثلِ OpenPDF/iText؛ قالبِ HTML→PDF ساده‌تر است اگر از قبل قالب‌سازی دارید).

> این زیرشاخه (پخش/آزمون/گواهی) بزرگ‌ترین کارِ باقی‌مانده‌ی این سند است. پیشنهاد: **فازِ جدا** (فازِ H
> در نقشه‌ی راهِ زیر)، چون به تصمیمِ محصولی (سطح امنیتِ ویدیو، الگوی PDF) نیاز دارد.

## ۳) عمودیِ جدید: تست‌های روان‌شناسیِ قابل‌خرید

فقط در Psych-Mehrjoo هست؛ کاملاً جدید (نه توسعه‌ی چیزِ موجود).

### مدلِ سرور
```
psychtest package (مثلِ academy/clinic هم‌سطح):
  PsychTestEntity        { id, title, slug, price, productId, description,
                            resultMode: enum(AUTO, COUNSELOR) }
  PsychTestQuestionEntity{ id, testId, order, text, options: jsonb[{text, score}] }
  PsychTestRangeEntity   { id, testId, minScore, maxScore, interpretation }   -- فقط resultMode=AUTO
  UserPsychTestEntity    { id, userId, testId, status: enum(PURCHASED, IN_PROGRESS,
                            AWAITING_INTERPRETATION, COMPLETED), totalScore, interpretation,
                            interpretedByCounselorId, completedAt }
```
- خرید = محصولِ لینک‌شده (`PsychTestEntity.productId`) → با همان الگوی
  `ClinicAccessService.grantSessionCredits` ولی به‌جای اعتبارِ جلسه، یک ردیفِ
  `UserPsychTestEntity(status=PURCHASED)` می‌سازد (`PsychTestAccessService` جدید، هم‌الگو).
- انجامِ تست: `POST /api/psychtests/{id}/attempt` با پاسخ‌ها → اگر `resultMode=AUTO` بلافاصله
  `totalScore` را با `PsychTestRangeEntity` مچ کن و `interpretation` را ست کن، `status=COMPLETED`.
  اگر `COUNSELOR` → `status=AWAITING_INTERPRETATION`.
- ادمین: `POST /api/admin/psychtests/{userTestId}/interpret` برای ثبتِ تفسیرِ دستی توسط مشاور
  (`status → COMPLETED`).
- endpointهای ادمینِ تست‌ساز: CRUD کاملِ `PsychTestEntity` + سؤالات + بازه‌ها (مثلِ الگوی
  `AdminCourseService`/`AdminClinicService` موجود).

### مدلِ کلاینت
- `feature:psychtest` (کاربر): «فروشگاهِ تست» (لیست + خرید) + «تست‌های من» (کارتِ وضعیت) +
  صفحه‌ی «انجامِ تست» (سؤال‌به‌سؤال، شبیهِ `19-quiz.html` موجودِ آموزشگاه — می‌توان کامپوننتِ
  سؤال/گزینه را از آزمونِ آموزشگاه (بخشِ ۲) بازاستفاده کرد اگر آن اول ساخته شود؛ یا برعکس).
- `feature:admin:psychtest`: تست‌ساز (عنوان/قیمت/توضیح/حالتِ نتیجه + افزودنِ نامحدودِ سؤال/گزینه/بازه) —
  دقیقاً هم‌الگو با `feature:admin:academy`'s `AddLessonForm`.
- گیت‌شده پشتِ `BrandFeatures.psychTests` (پرچم از قبل در فازِ ۰ اضافه شد).

## ۴) پالایشِ نوبت‌دهی (عمودیِ مشاوره — موجود، نیاز به تکمیل)

عمودیِ `clinic` از قبل کامل است (رزروِ نوبت + اعتبارِ جلسه از خریدِ محصول). چیزی که در دیزاینِ
Psych-Mehrjoo هست ولی در کد نیست:
- **ساعاتِ کاریِ ادمین/مدتِ نوبت:** `TherapistEntity` باید `workStart`, `workEnd`, `slotDurationMinutes`
  بگیرد؛ ادمین به‌جای افزودنِ تک‌تکِ بازه‌ها (`AddSlotForm` فعلی)، یک بازه‌ی کاری وارد می‌کند و سرور
  خودکار اسلات‌ها را می‌سازد (`POST /api/admin/therapists/{id}/generate-slots?date=...`).
- **پروندهٔ مراجع/تاریخچه‌ی جلسات:** `PatientNoteEntity{appointmentId, counselorId, note, createdAt}`
  — دسترسی محدود به همان مشاور/ادمین (RBAC سخت‌گیرانه، طبق هشدارِ HANDOFF). این داده حساس است؛
  endpoint باید `@PreAuthorize` روی نقش/مالکیت داشته باشد، نه فقط ADMIN.
- **حضوری/آنلاین/تلفنی برای خدمت:** `TherapistEntity` یا خودِ محصولِ لینک‌شده باید `mode: enum
  (IN_PERSON, ONLINE, PHONE)` داشته باشد؛ اگر `IN_PERSON` → آدرس/مکان در صفحه‌ی جزئیات نمایش
  داده شود (هم‌الگو با آدرسِ دوره‌ی حضوری در بخشِ ۲).

## ۵) فیچرِ جدید و جنریک: مقایسه‌ی محصول

قابلِ استفاده در هر ۵ اپ (نه فقط عمودی‌های آموزشی/مشاوره)، پس پشتِ پرچمِ عمومیِ
`BrandFeatures.productComparison` (نه یک عمودیِ کامل، فقط یک روشن/خاموش).

- **بدونِ نیاز به تغییرِ سرور:** چون محصولات already از طریق `GET /api/products/{id}` یا
  جست‌وجو/فیلترِ موجود قابلِ دریافتِ دسته‌ای هستند، مقایسه می‌تواند کاملاً کلاینت‌ساید باشد.
- کلاینت: `feature:comparison` جدید (یا داخلِ `feature:catalog` اگر کوچک بماند) —
  `ComparisonViewModel` یک `Set<Long>` از شناسه‌ی محصولِ انتخاب‌شده نگه می‌دارد (در `core:data`
  با `DataStore` پایدار می‌ماند، شبیهِ الگوی «علاقه‌مندی‌های محلی» اگر وجود دارد، وگرنه ساده در
  حافظه کافی است چون معمولاً session-scoped است).
- UI: دکمه‌ی «➕ مقایسه» روی کارتِ محصول (در `ProductCard` مشترکِ `feature:catalog`) + یک نوارِ
  شناورِ پایین‌صفحه («۲ محصول برای مقایسه») + صفحه‌ی `ComparisonScreen` (جدولِ کنارِ‌همِ
  attributesِ محصولات، همان `ProductAttribute` جنریکِ موجود در `ProductEntity.attributes` —
  یعنی این فیچر به‌طورِ طبیعی با اسکیمای per-دستهٔ ساعت/عطر (بخشِ ۶) هم کار می‌کند چون attributes
  از قبل key-value است).
- محدودیتِ منطقی: فقط محصولاتِ همان دسته قابلِ افزودن به یک مقایسه باشند (UX رایجِ فروشگاه‌ها).

## ۶) اسکیمای محصولِ per‌دسته (ساعت/عطر) + اسپک‌کارت در صفحه‌ی محصول

خبرِ خوب: `ProductEntity.attributes` **از قبل جنریک و JSON است** (`ProductAttribute{key, value}`
لیست) — پس **نیازی به migration یا ستونِ جدید نیست**. فقط باید:
1. **ادمین موقعِ افزودنِ محصول** بتواند attributeهای پیشنهادیِ per دسته را ببیند (مثلاً وقتی
   دسته = «ساعت مچی» است، فرم `movement`, `caseSize`, `caseMat`, `waterRes`, `glass`, `strap`,
   `warranty` را به‌عنوانِ ردیف‌های پیشنهادی/آماده نشان دهد، نه اینکه ادمین کلید را از صفر تایپ کند).
   پیاده‌سازی: یک `Map<categorySlug, List<String>>` ثابت (یا از سرور قابلِ‌ویرایش) در
   `feature:admin:products`، در فرمِ Variants/Attributes فعلی.
2. **صفحه‌ی محصول (کلاینت)** یک کامپوننتِ «کارتِ مشخصاتِ فنی» بسازد که attributesِ شناخته‌شده
   (بر اساسِ key) را با آیکن/چیدمانِ جدول رندر کند — برای عطر: هرمِ رایحه (`notesTop/Heart/Base`)
   به‌صورتِ سه‌ردیفِ گرافیکی به‌جای جدولِ ساده (بصری‌تر، مطابقِ HANDOFFِ عطر). برای ساعت: جدولِ
   ساده‌ی مشخصات با آیکن کافی است.
   این یعنی دو کامپوننتِ جدید در `feature:details`: `TechnicalSpecsTable` (عمومی) و
   `ScentPyramid` (اختصاصیِ عطر، فقط وقتی `notesTop`/`notesHeart`/`notesBase` در attributes باشد).
3. **راهنمای بند/قاب (ساعت) و راهنمای غلظت/حجم (عطر)** جایگزینِ `SizeGuideDialog` می‌شوند —
   همان کامپوننتِ Dialog موجود، فقط محتوای متفاوت per دسته (یک پارامترِ `guideType` یا صرفاً
   محتوای HTML/متنِ متفاوت که از سرور/ثابت می‌آید).

> این بخش کاملاً «بصری» است، هیچ منطقِ دامنه‌ای جدید نمی‌خواهد — کمترین ریسک، می‌تواند اولین فازِ
> اجراییِ عملی باشد (فازِ G در نقشه‌ی زیر) چون سریع و مستقل از بقیه است.

## ۷) ایده‌های اضافیِ پیشنهادی (خواستِ صریحِ کاربر: «فیچرهای دیگه‌ای که میشه اضافه کرد»)

این‌ها درخواست نشده‌اند ولی طبیعیِ این نوع پلتفرم‌اند؛ فقط پیشنهادند، در نقشه‌ی راه به‌عنوانِ
فازِ اختیاریِ آخر (فازِ N) گذاشته شده‌اند:

- **یادآورِ نوبت/کلاس** (push/SMS پیش از شروعِ جلسه یا کلاسِ حضوری) — نیازِ زیرساختِ اعلان که
  HANDOFFِ مشاوره هم به آن اشاره کرده.
  در واقعی تلفن‌همراه با WorkManager/BGTaskScheduler یا سرویسِ push (FCM) قابلِ پیاده‌سازی است.
- **باندلِ دوره+تست** (مثلاً «تست شخصیت + مشاوره‌ی تفسیر» به‌عنوانِ یک محصولِ ترکیبی با تخفیف) —
  از سازوکارِ تخفیفِ موجود (`AdminDiscountsScreen`) با «محصولِ باندل» قابلِ ساخت است.
  می‌تواند از الگوی موجودِ کد تخفیف روی چند SKU استفاده کند بدون مدلِ دیتای جدید.
- **امتیازدهی/نظرِ دوره و مشاور جدا از نظرِ محصول** (چون تجربه‌ی «دوره دیدن» یا «جلسه‌ی مشاوره»
  متفاوت از «خریدِ کالا»ست) — می‌تواند از همان `ProductReviewEntity` موجود استفاده کند چون هر
  دوره/خدمت already یک `productId` دارد؛ فقط برچسبِ UI فرق می‌کند («نظرِ شاگردان» به‌جای «نظرِ خریداران»).
- **گزارش‌گیریِ مالیِ per‌عمودی در داشبوردِ ادمین** (مثلاً «درآمدِ آموزشگاه» جدا از «درآمدِ فروشگاه»
  جدا از «درآمدِ مشاوره») — `AdminStatsController` موجود می‌تواند یک breakdown اضافه کند اگر
  `OrderItem`/`Course`/`Therapist` را به هم لینک کند (لینک از قبل هست چون هر دو از طریقِ
  `productId` به سفارش وصل‌اند).
- **حالتِ «معلق»/Waitlist برای کلاسِ حضوریِ پرشده** (وقتی `seatsTaken == capacity`) — کاربر
  می‌تواند نام‌نویسیِ لیستِ انتظار کند، مشابهِ «موجود شد خبرم کن»ی که برای موجودیِ محصول از قبل
  ساخته شده (`StockNotificationEntity`، بخشِ ۲ سندِ قبلی) — دقیقاً همان الگو قابلِ بازاستفاده است.

## ۹) نکاتِ فنیِ تکرارشونده (برای هر فازِ بالا رعایت شود)

- هر جدولِ جدید → یک migration idempotent در `db/init/NNN_*.sql` (الگوی موجود).
- هر ویژگیِ حساس/مالی (اعتبار، اسلات، ظرفیتِ کلاس) → قفلِ pessimistic مثلِ
  `SessionCreditRepository.findByUserIdAndTherapistIdForUpdate` موجود، تا رزروِ همزمان باگ نسازد.
  عدد باقیمانده باید در ترنزکشن `SELECT ... FOR UPDATE` خوانده شود، وگرنه دو کاربرِ همزمان
  می‌توانند آخرین صندلی/اعتبار را هردو بردارند.
- هر عمودیِ جدید → پشتِ یک پرچمِ `BrandFeatures` جدید و UIِ آن (nav + تبِ ادمین) شرطی.
- هر ماژولِ Gradleِ جدید → باید هم در `settings.gradle.kts` include شود، هم به‌طورِ صریح در
  `composeApp/build.gradle.kts` (نه فقط ماژولِ ادمینِ محصولات) — طبق نکته‌ای که در سندِ قبلی
  کشف شد (`implementation` گِرادل transitively برای compileِ composeApp دیده نمی‌شود).
- محیطِ ابری قادر به build نیست — هر فاز باید روی دستگاهِ شما کامپایل/QA شود؛ اگر خطا گرفتید،
  متنِ خطا را بفرستید تا فوری اصلاح شود (همان روالِ فازهای قبلی).
