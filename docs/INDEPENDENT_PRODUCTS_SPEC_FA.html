تعریف محصولات مستقل، فروش قابلیت‌ها و اپ‌ساز Carmilla

تاریخ: ۶ سپتامبر ۲۰۲۶ — وضعیت: نیازمندی و معماری هدف؛ این سند به معنی آماده‌بودن قابلیت‌ها برای فروش نیست.

این سند درخواست جدید مالک محصول را توضیح می‌دهد و برای کارهای باقی‌مانده بر توصیف‌های قدیمی «پوسته فقط نمایش است» و «همه خدمات فقط در Bridge اجرا می‌شوند» تقدم دارد. صف اجرا در tasks.md، معیارهای اجرایی در چک‌لیست مادر و تصمیم جایگزین در ADR-006 ثبت می‌شوند. کارهای DONE و شواهد گذشته، تاریخچه هستند و به‌تنهایی انطباق با این نیاز جدید را ثابت نمی‌کنند.

تعریف صریح مطابق توضیح دوباره مالک محصول

سه چیز می‌سازیم: یک پوسته مستقل؛ یک افزونه مستقل؛ و چهار نوع کلاینت Android، iOS، Desktop و PWA. خروجی Web مستقل نیز طبق درخواست اولیه حفظ می‌شود؛ PWA نسخه نصب‌پذیر وب است.

در زمان ساخت ZIP، واقعاً انتخاب می‌کنیم چه کدی داخل بسته باشد. برای پوسته و افزونه جداگانه یک مانیفست بسته داریم. این فایل تعیین می‌کند فروشگاه، آموزش، نوبت‌دهی، مشاوره و بیلدر هر پلتفرم داخل ZIP باشند یا نباشند. اگر بیلدر iOS انتخاب نشده، ماژول و صفحه اختصاصی آن در بسته تحویلی قرار نمی‌گیرد؛ صرف مخفی‌کردن دکمه کافی نیست. حذف ماژول نباید کتابخانه مشترک لازم برای قابلیت دیگری را حذف کند.

مثال زیر طرح ورودی مورد انتظار سازنده بسته است، نه فایلی که ابزار ساخت فعلی همین حالا پشتیبانی کند. نام کلیدهای تازه مانند clinic.consultation در کارت039 نهایی و با قرارداد فعلی سازگار می‌شوند:

{
  "schemaVersion": 1,
  "artifactKind": "theme",
  "sku": "theme-booking-android-pwa",
  "features": {
    "commerce.core": true,
    "academy.core": false,
    "clinic.booking": true,
    "clinic.consultation": false,
    "psych.tests": false
  },
  "builders": {
    "android": true,
    "ios": false,
    "desktop": false,
    "pwa": true
  }
}

خروجی این مثال یک ZIP پوسته دارای فروشگاه، نوبت‌دهی، بیلدر Android و بیلدر PWA است؛ ماژول آموزش، مشاوره، تست روان‌شناسی و بیلدرهای iOS/Desktop در آن نیستند. همین ساختار با artifactKind: "plugin" یک ZIP افزونه مستقل تولید می‌کند که با قالب دیگری کار می‌کند. برای نسخه UI پایه، قابلیت‌های دامنه و همه بیلدرها false هستند و فقط اجزای پایه لازم بسته‌بندی می‌شوند. وابستگی ضروری هر انتخاب، پیش از build صریح نمایش داده و اعتبارسنجی می‌شود؛ ابزار نباید فیچر پولی انتخاب‌نشده را بی‌خبر اضافه کند.

بیلدر هر پلتفرم یک فیچر جدا برای خرید و بسته‌بندی است. از پنل همان پوسته یا افزونه انتخاب‌شده، مشتری خروجی واقعی هدف را درخواست و دریافت می‌کند. رابط/adapter داخل ZIP است؛ عملیات سنگین compile/sign در سرویس ساخت جدا انجام می‌شود. خاموش‌کردن بیلدر iOS نباید بیلدر Android یا PWA را خاموش کند.

هر چهار کلاینت دو راه دریافت داده دارند: SPRING برای سرور Kotlin/Spring Boot، یا WORDPRESS برای API پوسته تنها، افزونه تنها، یا نصب هم‌زمان سازگار آن‌ها. برای اتصال به WordPress، داشتن یکی از دو محصولِ دارای قابلیت لازم کافی است. خرید قابلیت «ساخت اپ» از حق اتصال و کارکرد اپ تحویل‌شده جداست؛ خاموشی بیلدر، API داده اپ را خاموش نمی‌کند.

پس سه نوع تنظیم را نباید یکی گرفت: مانیفست ساخت بسته تعیین می‌کند کد چه چیزی تحویل شود؛ تنظیمات مشتری تعیین می‌کند کدام قابلیت موجود و خریداری‌شده روشن باشد؛ مانیفست runtime به سایت و کلاینت اعلام می‌کند اکنون چه چیزی قابل استفاده است. برای افزودن قابلیت حذف‌شده از ZIP، نسخه جدید لازم است؛ برای روشن‌کردن قابلیت موجود و مجاز، نسخه جدید لازم نیست.

۱. دقیقاً چه محصول‌هایی خواهیم داشت؟

خانواده محصول خروجی قابل تحویل بدون کدام محصول کار می‌کند؟ مسئولیت کامل
پوسته Carmilla فایل ZIP قابل نصب از بخش پوسته‌ها بدون افزونه Carmilla ظاهر سایت، تنظیمات، منطق و API قابلیت‌های خریداری‌شده و اپ‌ساز در صورت خرید
افزونه Carmilla؛ نام فنی فعلی Carmilla Bridge فایل ZIP قابل نصب از بخش افزونه‌ها بدون پوسته Carmilla منطق، مدیریت، API و صفحات/فرم‌های قابل استفاده قابلیت‌های خریداری‌شده روی قالب‌های استاندارد دیگر؛ اپ‌ساز در صورت خرید
کلاینت‌های مستقل Carmilla Android، iOS، Desktop، Web و PWA بدون اجبار به خرید هم‌زمان پوسته و افزونه برنامه مستقل با هویت، برند و بسته قابلیت‌های خودش؛ دریافت داده از یکی از دو پروفایل backend

سرور Kotlin/Spring Boot نیز خروجی قابل استقرار مستقل برای تأمین داده کلاینت‌هاست. سرویس ساخت برنامه زیرساخت جداگانه‌ای است که خروجی کلاینت‌ها را می‌سازد؛ با backend داده مشتری یک مفهوم نیست، حتی اگر در آینده در یک استقرار مدیریت شوند.

استقلال در این درخواست یعنی استقلال پوسته و افزونه Carmilla از یکدیگر. طبق پاسخ صریح مالک محصول، WooCommerce برای فروشگاه مجاز است. WordPress، WooCommerce در قابلیت‌های وابسته، زیرساخت پیام/پرداخت انتخاب‌شده و زیرساخت ساخت همچنان پیش‌نیازهای روشن خود را دارند. موتور فروشگاه جدیدی جای WooCommerce نوشته نمی‌شود.

۲. محصول پوسته؛ از UI پایه تا نسخه کامل

نسخه پایه، قالب عادی با طراحی، برگه‌ها، ناوبری، وبلاگ و تنظیمات ظاهری است. خرید فروشگاه، آموزش، معرفی مشاور، نوبت‌دهی، خدمات مشاوره، تست روان‌شناسی یا اپ‌ساز، بسته تحویلی را متناسب با همان انتخاب گسترش می‌دهد. هر نسخه پوسته باید همان قابلیت‌های درج‌شده در فاکتور خود را بدون نصب Carmilla Bridge اجرا کند؛ داشتن فایل HTML یا صفحه دوره به‌تنهایی تحقق این شرط نیست.

مثلاً «پوسته + نوبت‌دهی» باید نمایش متخصص، زمان‌بندی، ثبت نوبت، مشاهده و مدیریت نوبت و API مربوط را از همان بسته پوسته فراهم کند. اگر پرداخت جلسه نیز فروخته شده است، پیش‌نیاز پرداخت/WooCommerce باید در همان بسته تجاری اعلام شود. نبود افزونه Carmilla نباید علت خاموش‌شدن این قابلیت باشد.

منطق در فایل‌های نمایشی پراکنده نمی‌شود: پوسته یک هسته داخلی بسته‌بندی‌شده دارد و templateهایش از خدمات همان هسته استفاده می‌کنند. این هسته افزونه پنهان یا نصب‌شونده جدا نیست؛ هیچ نصب خودکار companion plugin یا MU-plugin برای تحقق استقلال لازم نیست.

۳. محصول افزونه؛ قابلیت واقعی روی قالب دیگر

خریدار افزونه می‌تواند قالب موجود خودش را نگه دارد. پس از نصب نسخه مناسب افزونه، هم بخش مدیریت و API و هم مسیر استفاده بازدیدکننده در سایت در دسترس قرار می‌گیرد؛ مثلاً فهرست دوره، صفحه درس، فرم رزرو و نوبت‌های من.

برای این کار افزونه باید صفحات، shortcode/block یا نمایش پیش‌فرض با CSS محدود به اجزای خودش داشته باشد. پوسته Carmilla می‌تواند همین نمایش‌ها را با template override زیباتر یکپارچه کند، ولی اصل قابلیت به آن وابسته نمی‌شود. «سازگاری با قالب‌های استاندارد» هدف معماری است؛ نام و نسخه قالب‌هایی که واقعاً آزمایش شده‌اند در ماتریس پشتیبانی درج می‌شود.

۴. چگونه چند نسخه بفروشیم و به‌ازای هر قابلیت هزینه بگیریم؟

یک کد اصلی و کاتالوگ قابلیت نسخه‌دار نگه می‌داریم. سازنده بسته، از روی شناسه محصول، SKU و فهرست قابلیت‌های انتخاب‌شده، ZIP یا خروجی کلاینت مناسب را می‌سازد. برای هر مشتری یک fork دائمی از سورس ایجاد نمی‌شود.

نمونه بسته تجاری محتوای خرید کنترل مشتری
Theme Base UI پایه و امکانات عمومی اعلام‌شده تنظیم ظاهر و محتوای پایه
Theme + Academy پایه + آموزش و زیرقابلیت‌های خریداری‌شده روشن/خاموش‌کردن آموزش
Theme + Booking پایه + معرفی ارائه‌دهنده خدمت و نوبت‌دهی روشن/خاموش‌کردن نوبت‌دهی
Plugin + Consultation مدیریت و نمایش خدمات مشاوره روی قالب دیگر روشن/خاموش‌کردن اجزای خریداری‌شده
هر محصول + App Builder حق ساخت برای پلتفرم‌های خریداری‌شده تنظیم برند، درخواست ساخت، وضعیت و دریافت خروجی
بسته کامل یا ترکیبی مجموعه انتخابی از قابلیت‌ها کنترل جداگانه هر قابلیت با رعایت وابستگی‌ها

این نام‌ها مثال محصول‌اند؛ قیمت، تعداد سایت، مدت پشتیبانی، تعداد build، هزینه امضا/زیرساخت و حق تمدید باید در کارت‌های تجاری تعیین شوند. در برنامه حاضر عدد قیمت یا قرارداد پرداختی اختراع نمی‌شود.

سه مفهوم باید جدا ذخیره شوند:

  1. قابلیت موجود در بسته: کد و منابع آن در ZIP/خروجی تحویلی قرار گرفته‌اند.
  2. مجوز خرید: این سایت یا پروژه حق استفاده از آن قابلیت و هدف خروجی را دارد.
  3. انتخاب مدیر: مشتری قابلیت مجاز را در تنظیمات روشن یا خاموش کرده است.

قابلیت مؤثر در سایت فقط وقتی روشن است که کد موجود باشد، مجوز معتبر باشد، مدیر آن را روشن کرده باشد، وابستگی‌هایش برقرار باشند و نسخه قابلیت مجوز انتشار داشته باشد. کلاینت نیز همین نتیجه را با سقف قابلیت‌های کامپایل‌شده و سیاست پلتفرم خود محدود می‌کند. Manifest گزارش وضعیت معتبر است؛ checkbox یا JSON عمومی، سند خرید نیست.

نسخه پایه می‌تواند برای معرفی امکانات، نام قابلیت‌های دیگر را نمایش دهد؛ کد پولی بسته‌نشده نباید از طریق toggle یا درخواست مستقیم قابل اجرا شود. برای ارتقا، بسته جدید متناسب با خرید تحویل می‌شود و مجوز آن به‌روز می‌گردد. اگر کد از قبل در خروجی نصب‌شده و مجاز باشد، روشن/خاموش‌کردن به rebuild احتیاج ندارد؛ قابلیت خارج از سقف نسخه نصب‌شده به به‌روزرسانی بسته/اپ نیاز دارد.

مدرک خرید می‌تواند همراه بسته، به‌صورت manifest امضاشده و قابل بررسی محلی تحویل شود. نیازمندی کاربر اجبار به اتصال دائمی سایت به سرویس لایسنس را ایجاد نمی‌کند؛ اتصال آنلاین برای خدمات اختیاری ساخت/تمدید/update طبق قرارداد جداست. حق استفاده محلی و کنترل هزینه jobهای سرویس ساخت با هم یکی نیستند.

۵. تنظیمات مشتری چگونه رفتار می‌کند؟

در هر محصول، صفحه «قابلیت‌های Carmilla» وضعیت را روشن نشان می‌دهد: خریداری‌نشده، نیازمند ارتقای بسته، آماده و خاموش، فعال، پیش‌نیاز ناقص، یا محدود به نسخه/پلتفرم.

فقط مدیر مجاز می‌تواند تنظیمات را تغییر دهد. روشن‌کردن قابلیت خریداری‌نشده یا ترکیب وابستگی نامعتبر هم در UI و هم در API رد می‌شود. خاموش‌کردن آموزش، نوبت‌دهی یا اپ‌ساز اطلاعات موجود را حذف نمی‌کند. مسیرهای عمومی و عملیات جدید قابلیت خاموش بسته می‌شوند؛ رسیدگی به سفارش/بازپرداخت قبلی و export مدیریتی طبق مجوز عملیاتی جداگانه حفظ می‌شود و راه دورزدن خاموشی نمی‌سازد.

آموزش، معرفی مشاور، نوبت‌دهی، جلسه مشاوره، پرونده خصوصی و تست روان‌شناسی یک کلید تجاری واحد نیستند. کاربر باید بتواند نوبت‌دهی را بدون خرید تست روان‌شناسی یا پرونده بالینی داشته باشد. شناسه‌های موجود مانند academy.core، clinic.booking و psych.tests حفظ می‌شوند؛ شناسه‌های جدید برای تفکیک مشاوره در قرارداد کاتالوگ تعیین و با alias/migration سازگار معرفی می‌شوند، نه با تغییر بی‌خبر رشته‌های فعلی.

۶. اگر پوسته و افزونه با هم نصب شوند چه می‌شود؟

هر ZIP از یک سورس مشترک به نام مفهومی carmilla-core بسته‌بندی می‌کند. این اشتراک در زمان توسعه است؛ مشتری برای اجرای یکی مجبور به نصب دیگری نیست.

در نصب هم‌زمان، یک هماهنگ‌کننده نسخه، فقط یک هسته سازگار را راه می‌اندازد. CPT، route، cron، جدول، migration، callback پرداخت و build request نباید دو بار ثبت یا اجرا شوند. تقدم به این معنا نیست که «هر فایل زودتر لود شد برنده است»؛ نسخه هسته، API و schema باید پیش از شروع خدمات بررسی شوند. در ناسازگاری، ماژول ناسازگار با پیام قابل اقدام متوقف می‌شود و هسته سازگار موجود تا حدی که schema اجازه می‌دهد ادامه می‌دهد؛ downgrade کور پایگاه داده ممنوع است.

داده متعلق به سایت است. منطق ثبت و دسترسی متعلق به هسته مشترک است. تنظیمات طراحی وب متعلق به پوسته است. هر دو ورودی تنظیمات قابلیت، وضعیت یکسان سایت را می‌خوانند. مجوزهای خرید باید برای همان سایت معتبر و به محصول/بسته مبدأ قابل انتساب باشند؛ نصب یک فایل ZIP به‌تنهایی مجوز دیگری ایجاد نمی‌کند. استفاده مشترک از قابلیت‌های دو خرید فقط مطابق entitlement همان سایت و سازگاری ماژول‌های موجود انجام می‌شود. مجوز متعلق به یک سایت دیگر، union ساده booleanها یا وجود پوشه افزونه مجوز محسوب نمی‌شود.

تعویض پوسته یا غیرفعال‌کردن یکی از دو میزبان، در صورت باقی‌بودن میزبان سازگار و مجاز دیگر، باید خدمات مشترک را حفظ کند. اگر تنها میزبان نصب‌شده نیز غیرفعال شود، اجرای خدمات و API متوقف می‌شود، ولی اطلاعات پاک نمی‌شود. استقلال نمی‌تواند به معنی اجرای کد پوسته‌ای باشد که دیگر فعال نیست. انتقال داده و مجوز به میزبان دیگر، حفظ شناسه‌ها و بازگشت‌پذیری باید آزمایش شوند؛ حذف دائمی داده فقط با عملیات صریح پاک‌سازی مجاز است.

۷. اپ‌ساز؛ قابلیت قابل خرید در هر دو محصول

پوسته دارای App Builder باید به‌تنهایی تمام تجربه ساخت را عرضه کند. افزونه دارای App Builder نیز با قالب دیگر همین تجربه را دارد: اتصال سایت، انتخاب هدف، تنظیم برند و هویت، انتخاب قابلیت‌های مجاز، پیش‌نمایش تنظیمات، درخواست، مشاهده وضعیت/خطا و دانلود خروجی.

Desktop بسته نصب برای سیستم‌عامل‌های اعلام‌شده runner و امضا/به‌روزرسانی مربوط به هر OS

WordPress درخواست ساخت را به سرویس ساخت می‌فرستد. Gradle، Xcode و ابزار بسته‌بندی روی runnerهای ایزوله اجرا می‌شوند؛ کلید امضای اپ در وردپرس مشتری قرار نمی‌گیرد. سرویس می‌تواند مدیریت‌شده توسط فروشنده یا طبق قرارداد قابل استقرار جداگانه باشد؛ در هر دو حالت پوسته و افزونه از یکدیگر مستقل‌اند. ساخت iOS به میزبان macOS و Xcode نیاز دارد؛ این محدودیت با گذاشتن دکمه در پنل وردپرس حذف نمی‌شود. مستند رسمی Kotlin

مجوز اپ‌ساز، مجوز قابلیت دامنه و مجوز پلتفرم خروجی از هم جدا هستند. خرید Android به‌طور خودکار مجوز iOS نیست؛ خرید اپ‌ساز هم مجوز آموزش یا مشاوره ایجاد نمی‌کند. وضعیت هدف‌ها در پنل باید واقعی باشد: زیرساخت/اتصال آزمایشی، آماده ساخت یا آماده تحویل تجاری. mock runner در فاز چهار فقط قرارداد را آزمایش می‌کند و خروجی تجاری محسوب نمی‌شود.

لغو اشتراک ساخت یا پایان اعتبار build نباید اپ تحویل‌شده یا داده سایت را خودکار نابود کند. سیاست روشن حق استفاده، build جدید، دریافت به‌روزرسانی، grace، انتقال دامنه و لغو مجوز در قرارداد تجاری تعریف و جداگانه enforce می‌شود. قطع شبکه مجوز نیز نباید به‌صورت ناخواسته همان معنی ابطال قطعی را داشته باشد.

۸. کلاینت مستقل با دو مسیر دریافت داده

هر خروجی کلاینت، برنامه مستقلی از یک کد مشترک KMP است؛ UI وردپرس یا پنل افزونه داخل آن شرط اجرا نیست. برای داده دقیقاً دو پروفایل دارد:

پروفایل منبع داده حالت‌های مجاز
SPRING سرور Kotlin/Spring Boot مستقل بدون نصب WordPress، پوسته یا افزونه Carmilla
WORDPRESS API مشترک Carmilla روی سایت WordPress پوسته تنها؛ افزونه تنها با قالب دیگر؛ یا هر دو محصول با یک هسته

سه حالت WordPress سه backend جدید یا سه fork کلاینت نیستند. endpoint کشف قابلیت و قرارداد REST مشترک‌اند و provider فعال سایت در metadata تشخیصی اعلام می‌شود. backend، برند، tenant، SKU، هویت برنامه و سقف قابلیت‌ها در تنظیمات ساخت مستقل از هم تعریف می‌شوند؛ نام برند تعیین‌کننده نوع backend نیست.

استقلال اپ یعنی artifact و چرخه انتشار مستقل، نه بی‌نیازی تمام امکانات از سرور یا امکان checkout آفلاین. تغییر backend/سایت یک اقدام تنظیمات کنترل‌شده است؛ credential و cache خصوصی سایت قبلی باید پاک/جدا شود. همگام‌سازی خودکار داده بین WordPress و Spring یا استفاده هم‌زمان از هر دو منبع در یک session در این درخواست تعریف نشده است؛ انتقال داده، فرآیند مهاجرت جدا دارد.

شواهد دقیق فایل/خط و محدودیت ممیزی در گزارش بازبرنامه‌ریزی قرار دارد. بررسی این نوبت ساختاری و استاتیک روی دو مخزن، کدهای کلیدی و کل صف بود؛ اجرای کامل برنامه‌ها، آزمون نفوذ، تأیید دستی محصول و ممیزی خط‌به‌خط همه فایل‌ها انجام نشده است. یافته‌های قدیمی امنیتی بدون بررسی مجدد، به‌عنوان نقص فعلی تکرار نشده‌اند.

۱۱. ترتیب اجرا و معیار تحویل

ابتدا شواهد متناقض فاز سه بازبینی و تنظیمات ساخت/Manifest runtime تکمیل می‌شوند. سپس قرارداد سه خانواده محصول، کاتالوگ SKU و هسته مشترک در فاز چهار اجرا می‌شود. دامنه‌های بزرگ به کارت‌های کوچک‌تر محتوا، فروشگاه، آموزش، نوبت، تست، پشتیبانی و تعاملات تقسیم می‌شوند. پس از آن نصب مستقل، تنظیمات خرید، ارتقای بسته و سازگاری هم‌زمان آزمایش می‌شوند.

فازهای پرداخت، پیام‌رسانی، انتقال داده، وب/PWA، Android، آموزش، کلینیک، Spring، iOS و Desktop حفظ می‌شوند؛ وابستگی‌های صرفاً تاریخی حذف و وابستگی واقعی Gateها ثبت می‌شود. ترتیب صف اولویت کار است، نه اینکه استقلال یک محصول به پایان همه محصولات دیگر وابسته باشد. هیچ فیچر یا خروجی قبل از Gate مخصوص خودش به‌عنوان آماده فروش معرفی نمی‌شود؛ P04 آماده‌سازی میزبان‌هاست و جای Gateهای تخصصی را نمی‌گیرد.

حداقل ماتریس پذیرش:

  1. پوسته تنها، با WooCommerce فقط در سناریوهای وابسته: قابلیت خریداری‌شده از صفحه تا ذخیره داده و API کار کند.
  2. افزونه تنها روی قالب پیش‌فرض و قالب ثالث: کاربر سایت بدون اپ هم بتواند از صفحات و فرم‌های قابلیت استفاده کند.
  3. هر دو با هم: یک ثبت/نوشتن، یک وضعیت تنظیمات و یک build برای یک درخواست؛ تغییر ترتیب نصب یا نسخه موجب تکرار نشود.
  4. بسته پایه، بسته تک‌قابلیت و ترکیبی: قابلیت خریداری‌نشده از UI، لینک مستقیم، API و job باز نشود؛ قابلیت مجاز روشن/خاموش شود.
  5. ارتقای SKU، به‌روزرسانی، خاموشی و جابه‌جایی میزبان: داده و هویت قبلی حفظ و مسیر بازگشت مشخص باشد.
  6. هر کلاینت: SPRING و WORDPRESS با قابلیت‌های اعلام‌شده و artifact واقعی همان پلتفرم تست شوند؛ fixture به‌عنوان production evidence معرفی نشود.
  7. اپ‌ساز: Theme-only و Plugin-only هر یک به‌تنهایی خروجی واقعی هدف خریداری‌شده بسازند و تحویل دهند.

برای تغییر UI، شبکه یا مهاجرت، کارت باید «کجا نگاه کنیم، چگونه تست کنیم، نتیجه موفق چیست» را تعریف کند و تا تأیید انسانی AWAITING_MANUAL_QA بماند. تغییر این مستندات آزمون دستی محصول محسوب نمی‌شود.

پذیرش کامل این درخواست در فاز P18 انجام می‌شود: آزمون خودکار ماتریس،تست انسانی پوسته تنها،تست انسانی افزونه تنها،تست چهار کلاینت با هر دو backend و Gate نهایی مالک محصول. تا پایان آن،کامل‌بودن همه خروجی‌های درخواستی ادعا نمی‌شود.

۱۲. کانال فروش

نسخه پوسته دارای منطق دامنه باید با الزامات مارکت انتخابی سنجیده شود. قواعد مخزن رسمی WordPress.org برای Theme، قابلیت‌هایی مانند CPT و shortcode را داخل پوسته نمی‌پذیرد؛ این قاعده درباره همان کانال است و نباید بدون بررسی به مارکت‌های دیگر تعمیم داده شود. در صورت نیاز به WordPress.org، خروجی UI-only جداگانه می‌تواند تعریف شود و نباید جای وعده پوسته مستقلِ دارای قابلیت را بگیرد. راهنمای رسمی انتشار پوسته

جزئیات قرارداد، قیمت، تعداد build و پلتفرم‌های مجاز باید در صفحه فروش هر SKU شفاف باشند. مشتری باید بداند فایل خریداری‌شده چه قابلیت‌هایی دارد، کدام‌ها را می‌تواند خاموش/روشن کند، چه پیش‌نیازهایی لازم است و کدام هزینه‌ها مربوط به ساخت و پشتیبانی آینده‌اند.
