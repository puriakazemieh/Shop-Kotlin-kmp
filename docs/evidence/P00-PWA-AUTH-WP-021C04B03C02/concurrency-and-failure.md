# P00-PWA-AUTH-WP-021C04B03C02 — آزمایش هم‌زمانی و شکست

تاریخ اجرا: ۲۰۲۶-۱۰-۱۸. **نتیجه پذیرش: BLOCKED**. این آزمایش شاهد پژوهشی است، نه راهکار امنیتی قابل استقرار، تست سایت واقعی یا اثبات رفع ورود PWA.

## محیط و بازتولید

- MariaDB `10.6.28` در کانتینر موقت، بدون port منتشرشده یا mount وردپرس کاربر و با `/var/lib/mysql` روی tmpfs؛ هر اجرای PHP یک prefix تصادفی و جداول جدا داشت.
- سه اجرای مستقل با WordPress `6.4.3` / PHP `8.1.27`، WordPress `6.6.2` / PHP `8.2.25` و WordPress `7.1.3` / PHP `8.3.35` انجام شد. fixture قبلی بدون تغییر ابتدا اجرا می‌شود. `php -l` پاس شد و اجرا بدون flag/prefix موقت رد شد.
- اسکریپت: [experiment-identity-shared-concurrency.php](../../../wordpress/carmilla-bridge/tests/experiment-identity-shared-concurrency.php). workerهای جداگانه اتصال‌های مستقل به همان database مصنوعی دارند، قبل از شروع با barrier هماهنگ می‌شوند و فقط داده ساختگی به‌کار می‌رود. اسکریپت در پایان به‌دلیل مانع مشاهده‌شده عمداً nonzero خاتمه می‌یابد؛ در این اجرا `docker run` کد `1` گزارش کرد. `PASS`های سناریوهای محدود به‌معنی PASS شدن gate نیستند.
- هیچ سایت حفظ‌شده، route، migration، schema واقعی یا OTP تغییر نکرد. ایمیل ارسال نشد. جدول‌ها، trigger و fault injection فقط در prefix تصادفی نصب آزمایشی ساخته شدند.

## خلاصه نتایج هر سه نسخه

| سناریو | نتیجه مشاهده‌شده |
|---|---|
| رقابت افزودن موبایل با WordPress و SQL برای دو مالک | SQL اعمال شد؛ WordPress با خطای `1644` رد شد؛ یک مالک و یک مرجع باقی ماند. callback پیش از درج وردپرس اجرا شد ولی callback پس از درج خیر. |
| تغییر موبایل WordPress در برابر تغییر login با SQL | تغییر login اعمال و تغییر موبایل با `1644` رد شد؛ سازگاری claimها پس از عملیات برقرار بود. |
| حذف یک ردیف تکراری در برابر تصاحب مالک دیگر | حذف انجام و تصاحب رد شد؛ login و یک ردیف موبایل مالک اولیه باقی ماندند. |
| موبایل WordPress در برابر email با SQL | SQL اعمال و WordPress با `1644` رد شد؛ یک مالک باقی ماند. email عددی عمداً fixture باینری و اعتبار ایمیل محصول نیست. |
| تغییر `user_id` metadata | با مرجع دیگر از مالک قبلی رد شد؛ در حالت تک‌مرجعی، انتقال صریح SQL پذیرفته و مالک جدید ثبت شد. این نتیجه سیاست مجوز انتقال یا تأیید امنیت production نیست. |
| کاربر ناموجود، مقدار نامعتبر، و rollback | درج‌های نامعتبر رد شدند؛ rollback داده آزمایشی را برگرداند ولی callbackهای WordPress قبلاً اجرا شده بودند. برای side effect فقط شمارنده داخل حافظه مشاهده شد؛ هیچ سرویس خارجی فراخوانی نشد. |
| بن‌بست عمدی روی دو claim | یک worker با `1213` و دیگری با تعارض `1644` رد شد؛ مالکیت اولیه پس از rollback حفظ شد. |
| حذف SQL و افزودن metadata هم‌زمان در دو snapshot، با نگه‌داشتن تراکنش‌ها تا پایان هر دو عملیات | حذف اعمال و درج با timeout `1205` رد شد؛ در این زمان‌بندی ناسازگاری claim مشاهده نشد. این مشاهده به همه ترتیب‌های ممکن تعمیم‌پذیر نیست. |

## مانع بازتولیدشده: حذف نیمه‌کاره با گزارش موفق

برای شبیه‌سازی شکست مشخص، یک trigger موقت فقط حذف یک ردیف `cb_mobile` کاربر کاملاً ساختگی را با خطای database رد کرد. سپس `wp_delete_user` واقعی فراخوانی شد. در **هر سه نسخه** مشاهده شد:

```text
returns_true=1 user_survives=1 mobile_survives=1 metadata_partial=1
deleted_meta_callback=1 deleted_user_callback=1
```

یعنی نتیجه WordPress `true` بود و callbackهای حذف اجرا شدند، ولی کاربر و موبایل او باقی ماندند و برخی metadata دیگر قبلاً پاک شده بودند. guard مدل از آزادشدن نادرست claim جلوگیری کرد، اما حذف کامل و گزارش صحیح یا بازگشت side effectها را تضمین نکرد. این یک failure injection محدود است و به معنی وقوع این خطا در سایت کاربر نیست. نتیجه را نباید با آزمون rollback یک statement تکی یا با حذف موفق عادی C01 یکسان گرفت.

## محدودیت و ادامه لازم

- کاربرد trigger در محصول یا وابستگی به آنها مجاز نشده است. رفتار سایر افزونه‌ها، چندسایته، تمام ترتیب‌های هم‌زمان، backfill، مجوز انتقال، normalization و side effectهای بیرونی اثبات نشده‌اند. `billing_phone` بخشی از هویت فرض نشده است.
- برای ادامه باید راهبرد lifecycle و مرز تراکنش/خطا برای حذف و تغییر کاربر و نیز شیوه برخورد با callbackهای قبلاً اجراشده به‌صورت مستقل طراحی و در fixture تست شود؛ صرف اطمینان از claim کافی نیست. تسک و والد آن تا رفع و بازآزمایی واقعی این مانع باز می‌مانند. اصلاح هسته WordPress یا ادعای حل OTP از این شاهد نتیجه نمی‌شود.
