# P00-PWA-AUTH-WP-021A — WordPress browser-session contract

Date: 2026-10-17. Status: design completed; **not implemented or security-tested**. Applies to the Bridge in this P00 repair, not a claim that Theme-only support is complete. Future work must preserve the independent-product architecture and reuse an appropriate shared implementation when that work is in scope.

Later status, 2026-10-18: this is the historical baseline and contract, not the current status of every client component. The separate [WEB-022A](../P00-PWA-AUTH-WEB-022A/verification.md) added partial bearer/redirect hardening and automated tests; full browser integration and compatibility remain unconfirmed. The legacy OTP race was reproduced in [C04C01](../P00-PWA-AUTH-WP-021C04C01/otp-concurrency.md) and remains unfixed.

## 1. Baseline and compatibility

- `CB_Auth_Controller` has mobile login/register/OTP/refresh, but no `/api/auth/web/*` routes. Its mobile authentication response contains `refreshToken` in JSON. `CB_JWT` currently provides a 15-minute access JWT, a 30-day refresh JWT, and user-wide timestamp revocation; it has no per-browser token rotation or replay record.
- `AuthApiImpl` selects `/api/auth/web/login`, `/register` and `/login-with-otp` on JS. JS uses Fetch credentials `include`. `AuthResponse.refreshToken` defaults to an empty string, whereas `RefreshTokenResponse.refreshToken` is currently required. `HttpClientFactory` currently requires a stored refresh token before attempting a refresh; startup only examines the memory token, and `AuthRepositoryImpl.signOut()` only clears local state. These facts are not evidence that web refresh, restoration, or logout works.
- Existing web reset calls use the mobile `/api/auth/reset-password` and `/reset-password-with-otp`; the Bridge returns its full mobile authentication response from these routes. The web client must not receive that response after this repair. Do not change the existing mobile response contract as a shortcut.
- Spring's documented cookie is `__Host-shop_refresh`. WP uses the per-installation name defined below; the client must not read or assume a cookie name, and Spring/mobile behavior remains unchanged. `P01-SECURITY-CODE-005C.md` has an `AWAITING_MANUAL_QA` header but also a historical DONE completion record; this design does not resolve that discrepancy or assert a new Spring test.
- The existing CORS code allows several localhost origins by default and only determines response headers. CORS response visibility is not a server-side authorization or CSRF check. `get_site_url()` may include a subdirectory, which is not part of an HTTP origin.
- `ApiConfig.isApprovedApiHost()` checks only the hostname. A hostname alone is not sufficient to scope bearer credentials across schemes or ports; WEB-022 must scope JS bearer injection and redirects to the approved API origin and intended base path, including scheme and port.

## 2. Routes and response

Under `carmilla/v1`, browser-only `POST /api/auth/web/login`, `/register`, `/login-with-otp`, `/refresh`, `/logout`, `/reset-password` and `/reset-password-with-otp` obey the guard in section 4. Login and registration keep the existing request DTO field names; OTP uses `mobile` and `otpCode`. OTP delivery retains the existing non-token-issuing send-OTP route, subject to its existing security controls. Authenticate through the appropriate WordPress authentication filters and preserve the existing mobile endpoints. Failed login must not create a session.

On successful login, registration, OTP login or refresh, return a short-lived `accessToken` and compatible `user` object, but **never** a refresh credential, cookie value or separate session identifier field in JSON, URLs, application logs or diagnostics. The signed access JWT's family reference is visible to its holder and must not itself authorize refresh, contain user data, or be treated as a secret. A normal response has `Cache-Control: no-store`; include appropriate no-cache behavior on errors too. The cookie contains only the opaque refresh credential, not profile data. `POST /web/logout` revokes the browser family and expires the cookie; a missing/invalid session is idempotent after guard checks. On storage failure, clear the local cookie if possible but return an error: do not claim server-side revocation succeeded.

Browser password reset routes use the existing reset verification semantics, invalidate all browser families for the account and return no tokens; the user must log in again. Every browser access-token check and refresh additionally compares the session's keyed password-state fingerprint to the current stored password hash, so direct `wp_set_password`/admin/CLI changes invalidate older browser sessions even if a revocation hook is missed. The fingerprint is `HMAC-SHA-256` of a domain-separated site/user/password-hash tuple under a server-only key and must never contain or expose plaintext passwords or the password hash. Include core reset, admin and programmatic password changes in integration tests. The current XAMPP WordPress exposes `wp_set_password`, `password_reset` and `after_password_reset` actions; hook behavior and compatibility with supported WP versions must be verified, not assumed. Mobile reset outputs and mobile token behavior are unchanged.

## 3. Cookie, installation separation, session lifecycle

- WordPress cookie name: `__Host-carmilla_wp_` followed by the first 32 lowercase hex characters of SHA-256 of a canonical, **trusted configured** site URL plus the blog ID with an unambiguous delimiter. Compute from configuration, never from the request Host header. The URL includes any installation path and explicit port. Stable for the same installation; on canonical URL/blog identity change, the old name/session is not reused and the user signs in again. Hash collisions, malformed URL and duplicate configuration fail closed. In multisite, derive per blog and keep data/blog binding separate.
- Cookie attributes: `Secure; HttpOnly; SameSite=Strict; Path=/`, no `Domain`; expiry no later than the session absolute deadline. The browser stores the cookie, never JavaScript localStorage/sessionStorage. `__Host-` cookies are host-wide and ignore port and path as isolation boundaries: the derived names avoid accidental overwrites by the multiple local WP sites and Spring, but they do **not** make mutually untrusted applications on one host safe. Use a dedicated trusted host for production deployments; local shared-host use is QA only. `SameSite=Strict` also rules out genuinely cross-site PWA deployments under this contract; do not silently switch to `None`.
- Generate at least 256 bits of cryptographically secure randomness per opaque refresh credential, and a separate unpredictable family ID. Store only SHA-256 credential digests, not raw credentials. Bind each family to user, installation/blog, creation time, absolute expiry, last-use/idle expiry, revocation state and keyed password-state fingerprint. Default absolute lifetime is 30 days from initial authentication, with a 14-day idle limit; rotation never extends the original absolute deadline. Expired/revoked records and spent-token digests are retained long enough to detect replay until the family expires; then prune on a bounded schedule without deleting user data.
- Use a transactional store with unique digest index and family-level row locking / atomic compare-and-swap. Find a digest, lock its family, recheck the current generation and validity, mark the old credential spent and insert the new digest in the same transaction. Send the new cookie only after commit. A spent credential replay revokes its family, including the newly rotated credential; other device families remain unaffected. Unknown credentials return the same generic unauthorized response and cannot revoke a family. Storage, random generation, key, clock, locking or transaction failure means no token/cookie is issued. Do not rely on non-atomic option/transient read-then-write or on user-wide timestamp-only JWT revocation.
- Two concurrent refreshes of the same old credential result in one initial rotation and one replay detection; after the replay, the entire family, including the first new credential, is revoked. The browser client must single-flight refresh including across tabs where supported; a race or interrupted/lost response may force re-login, and must never cause unsafe reuse or a silent authentication loop.
- A browser access JWT is type-scoped and bound to its family and installation, and is accepted only while the family and password fingerprint remain valid; its lifetime is at most 15 minutes. Browser logout, replay or password change therefore rejects the associated web access token immediately on the next protected request, not merely on expiry. Keep the mobile verifier and existing mobile JWT format/behavior compatible. Authorization still uses current server-side user capabilities; a JWT role claim is not an entitlement.

## 4. Origin, CSRF, TLS and local QA

- For every mutating `/web/*` request, validate the request on the server **before** authentication, registration, cookie creation or revocation: require `POST`, one explicit `Origin` exactly matching an administrator-configured trusted web origin after scheme/host/port normalization, `Content-Type: application/json`, and a non-simple custom header `X-Carmilla-Web-Request: 1`. Reject absent, `null`, malformed, multiple or unlisted origins and missing/incorrect headers. Reject simple content types and unsafe redirects. Same-origin is also checked against a configured trusted origin; do not derive trust from unvalidated `Host`, `Forwarded` or `X-Forwarded-*`. Do not authenticate a browser request solely because it contains an Origin: non-browser clients can forge it.
- CORS preflight for this web contract permits the custom header and only exact trusted origins with credentials; return `Vary: Origin`, never wildcard or `null` as an approved origin. Restrict allowed origins to controlled, trusted HTTPS same-site clients. The custom-header requirement and strict server-side Origin check protect login/registration as well as refresh/logout against browser CSRF; `SameSite` is defense in depth, not the sole control. XSS in an explicitly trusted origin is outside what this control alone can prevent.
- Production is HTTPS-only, including authentication and API; HSTS/proxy TLS configuration is a deployment requirement, not proof from this design. `is_ssl()` alone does not establish safe proxy trust. A reverse proxy must strip incoming forwarded headers, set them itself, restrict backend access to trusted proxy addresses and provide verified scheme/host to WordPress. Unknown proxy, ambiguous scheme or unsafe configuration fails closed. No trust of forwarded values solely because they are present.
- Local testing may use a **separate explicit, default-off QA-only HTTP exception**, not a production fallback. It requires all of: WordPress environment explicitly `local`, a dedicated opt-in flag in the QA configuration, configured WP/site and exact allowed browser origin `http://localhost` (optional explicitly listed localhost port), actual loopback client and server addresses, host exactly `localhost`, no proxy/forwarded headers, synthetic-only accounts and no non-local access. Any failed check rejects session issuance. Cookie attributes remain unchanged; some browsers treat localhost as an exception to Secure's HTTPS rule, so acceptance must be measured in the actual supported browser. This mode has no transport encryption and is not production evidence. If it cannot be safely confined or the browser rejects the cookie, use an isolated HTTPS QA instance with a trusted local certificate and same-site HTTPS PWA instead; do not weaken the production flags or delete/overwrite the existing WordPress installations or databases.

## 5. Required verification and handoff

1. Unit tests: token entropy/unique generations; digest-only persistence; fixed absolute/idle expiry; malformed, expired and unknown tokens; failed RNG/store/transaction; site/blog isolation; only the owning family revoked on logout; password fingerprint change; access-token acceptance only while family is active.
2. Real transactional integration tests: two concurrent uses of one refresh credential; one rotation followed by replay revokes the family; refresh versus logout/password reset race; rollback on failed commit; neither a stale token nor its replacement is usable after replay; separate device and site sessions survive unrelated logout. Check no partial family/session creation when credentials, CSRF or session setup fails. If registration created a WP user before a session-write failure, report the partial outcome accurately and never delete that user automatically.
3. Route tests: valid login/register/OTP; wrong credentials; exact success status/body; expired/missing/replayed cookie; both password-reset paths; allowlisted and hostile origins; absent/null/malformed origins; missing/wrong custom header; text/plain/form bodies; spoofed forwarded headers; TLS-required/default-off QA behavior; credentials never returned in body/URL/logs. Test legacy mobile endpoints separately for compatibility.
4. Real-browser integration after `WEB-022`: cookie attributes and distinct names for the two installations; login, registration, reload restoration, authenticated requests, rotation, logout and reset; concurrent tabs; cookie replay with synthetic accounts; absent credential values in Local Storage/Session Storage; redacted trace and exact build fingerprint. Check local HTTP QA is explicitly enabled and isolated, and separately test a TLS deployment before a release claim. P00-T05 needs owner confirmation; no payment, other product mode or release gate is implied.
5. Client follow-up: add only the guarded WP web header/routes, optional web refresh DTO, cookie-based refresh without requiring a stored refresh string, restoration, cross-tab coordination, real server logout, web reset endpoints, and strict origin/scheme/port bearer scoping. Preserve mobile and Spring behavior. This is `P00-PWA-AUTH-WEB-022`, not work performed by this card.

## 6. Sources and assessment limits

- [MDN Set-Cookie reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie): cookie attributes, host prefixes, site behavior, and localhost exception.
- [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): Origin validation, non-simple custom headers and restricted credentialed CORS.
- [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14): refresh rotation and replay detection. Carmilla's session protocol is not claimed to be OAuth; this is an analogous security design principle.
- [WordPress `is_ssl()`](https://developer.wordpress.org/reference/functions/is_ssl/): what WordPress checks; trusted-proxy handling requires additional deployment controls.

Review was static except for the previously recorded route-existence check in `P00-PWA-AUTH-WP-021`; no real login, security test, code change, database change or deployment was performed here. Design is an implementation contract, not a pentest or a passed security gate.
