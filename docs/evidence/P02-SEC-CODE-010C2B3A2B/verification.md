# P02-SEC-CODE-010C2B3A2B — booking partial-write repair

2026-11-02. Graph pre-edit impact on the actual `CB_Clinic_Controller` class was CRITICAL (146 impacted symbols, five affected processes); `book` was not separately resolved by the graph. Source search confirmed the public appointment route currently points to `disabled_feature`, while the direct controller method is tested here. The code change is confined to `book()`: verify posts/postmeta/bookings use InnoDB, begin a transaction, acquire the unique slot lock, create the appointment and required metadata, link and verify the booking row, calculate the DTO, then commit. On any failure it rolls back, invalidates post/meta caches and returns HTTP-style 503 `BOOKING_UNAVAILABLE`. A duplicate slot remains 409 `SLOT_TAKEN`.

Disposable installed WordPress fixture (WordPress 7.1.3, PHP 8.3.35, MariaDB 10.6.28), all three relevant tables confirmed InnoDB. `CARMILLA_LOGIN_DISPOSABLE=yes php tests/smoke-booking-atomic-real-wp.php`: exit 0, seven PASS/zero FAIL. Injected unreadable engine metadata and a MyISAM engine result both yielded 503 with zero lock/post/meta writes. Injected `wp_insert_post` SQL failure, first appointment metadata INSERT failure, and booking-row UPDATE failure each yielded 503 with zero residual lock, appointment post or metadata. Healthy booking yielded 201 with a linked lock, one post, five metadata rows, correct synthetic user ownership and DTO ID. Duplicate request yielded 409 with exactly one slot lock. Both PHP files passed `php -l`. After test cleanup, SQL checks found zero synthetic booking posts/users and zero booking rows whose therapist post is missing.

The review baseline in `docs/evidence/P02-SEC-REVIEW-010C2B3A2A/verification.md` had observed a residual lock or false 201 for all three injected faults. This focused test exercises the actual WordPress database and controller method. It does not claim public booking HTTP is enabled: that route is intentionally disabled in this phase. WordPress hooks may have non-database side effects beyond the InnoDB transaction; no external-effect atomicity is claimed. No production data was changed.
