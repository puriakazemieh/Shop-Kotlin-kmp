# P02-PERF-DISC-010C2B3B1A — bounded lesson questions decision

2026-11-02. Source and graph review: the current WordPress GET `/api/academy/lessons/{lid}/questions` returns a bare JSON list. KMP `AcademyApi.getLessonQuestions`, `AcademyApiImpl`, repository/domain use case and `CourseLearnViewModel` all consume a complete list; the lesson UI renders every item. Spring `LessonQuestionController.list` also returns a bare list. Replacing the existing response with a page envelope, or silently limiting it, would break existing clients or hide older questions. The 30,000-comment WordPress fixture measured a 30,000-row meta scan, 42.147 ms SQL and 119.908 ms controller latency for 15,000 returned questions. A temporary meta composite index was not selected by the optimizer (39.986 ms SQL), so an index alone is not a defensible fix.

Decision: preserve the legacy bare-list route until client migration. Add an **opt-in versioned page route** in the LMS phase, with a page size default 50 and maximum 100, deterministic ascending `(comment_date_gmt, comment_ID)` keyset cursor, and response `{items,nextCursor}`. The WordPress query must drive from course comments through an indexed course/type/approval/order path and test lesson metadata by comment ID, rather than scanning global `wp_commentmeta`. An opaque cursor must be validated and tied to the lesson; invalid cursors fail closed. A page of 100 on the 30,000-comment fixture should return in at most 20 ms SQL and avoid a full commentmeta scan, with no duplicates/gaps over sequential pages under a fixed snapshot. The exact threshold is a local synthetic QA target, not a production SLO.

The eventual client transition needs matching Spring pagination and KMP network/repository/ViewModel/UI support for incremental load, plus two-backend QA; that spans multiple product boundaries and exceeds M. The present P02 design makes no product API change and does not claim the legacy SlowDBQuery finding is fixed. A bounded WordPress endpoint task is queued for P13 after LMS ownership is settled; Spring/client parity must be separately decomposed before switching the client. Old clients retain the known unbounded route until a versioned deprecation decision.
