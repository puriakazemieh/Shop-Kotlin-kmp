# P00-PWA-AUTH-WP-021C04B02 — identity safety contract and research decision

Date: 2026-10-17. Status: design and bounded prototype decision, **not a production-ready implementation**. B01's source inventory and the B race reproduction are the factual baseline. This document does not modify either preserved site, impose an account policy, or declare a particular database extension compatible with every WordPress host.

## 1. Problem, threat boundary and required outcomes

The new browser-registration path must not create or silently attach to an ambiguous identity, issue a credential for a different user, or claim a failed account/session operation succeeded. It must respect the browser guard before mutations, server registration policy, WordPress validation/filters and current WordPress user identity. Successful browser responses use the existing `021A` token/cookie contract. Existing user records, IDs, purchases and capabilities are not deleted or merged automatically; untrusted identifiers are not proof that two records belong to the same person.

The scope includes concurrent ordinary SQL writes from supported WP core, WooCommerce and Carmilla entry points, even when they do not know about a new plugin lock. A privileged operator who can alter/drop triggers, change identity tables directly, restore old databases, install arbitrary PHP or modify server configuration is part of the deployment trust boundary; detecting such tampering solely by checking metadata before a request has a check/use race and is **not** a complete defense. Hostile third-party PHP/DB administrators and external identity providers are not automatically supported. A deployment must fail closed when the required trust/coverage cannot be established. SSO-only identifiers currently do not work in the isolated browser login helper.

The contract is *not* permission to disable existing mobile, WooCommerce, admin, imports or live registration. Their compatibility must be tested before any deployment. Legacy behavior is not made safe merely by adding a browser endpoint. Independent Theme/Plugin packaging remains future work; one active shared owner of a site identity service is required before claiming either product mode works independently.

## 2. Alternatives considered

| Candidate | Assessment |
|---|---|
| Preflight queries / WP filters alone | Rejected as a guarantee: two processes can pass them before either inserts, as the existing real-core test proves. Filters and `user_register` also do not cover arbitrary direct SQL. |
| Named/process lock or a plugin claim table consulted only by browser registration | Rejected as a global guarantee: another WP, WooCommerce or plugin writer can bypass it. A post-insert check can detect some conflicts but cannot prove it prevented them or undo side effects safely. |
| Independent unique indexes on WP login/email columns | Insufficient alone: they do not cover cross-namespace login-versus-email collisions, `cb_mobile`, multiple meta rows, legacy incompatible values or existing duplicates. Adding indexes to live core tables is not authorized. |
| **Database-enforced shared ownership, with transactional constraints and complete tested DML interception** | Selected only as a candidate for an isolated proof of feasibility. A single canonical claim may have several same-user source references but never two owners; ordinary source-table inserts/updates/deletes must update the claims in the *same database transaction*. DB-level interception might cover writers that do not cooperate at PHP level, subject to engine, permissions, collation, concurrency, cleanup and support constraints. It is not yet designed or tested sufficiently to enable on any real site. |
| Disable browser registration | Safe fallback. It remains unavailable unless the complete coverage and deployment gates below are independently proved. Existing unrelated paths are not silently disabled by this decision. |

MariaDB documents row-level trigger limitations and transactional error behavior; these facts make a synthetic investigation meaningful, not a warranty about compatibility, replication, arbitrary DDL or external writers. [Trigger overview](https://mariadb.com/docs/server/server-usage/triggers-events/triggers/trigger-overview), [trigger limitations](https://mariadb.com/docs/server/server-usage/triggers-events/triggers/trigger-limitations). WordPress itself invokes hooks and stores user metadata during `wp_insert_user`; a future design must test those side effects, not assume a database transaction reverses external actions. [WordPress `wp_insert_user`](https://developer.wordpress.org/reference/functions/wp_insert_user/).

## 3. Ownership and comparison contract

Each login-bearing identifier has a versioned equality key in a **single shared namespace** for `user_login`, nonempty `user_email` and `cb_mobile`. If several references are equal and belong to one WP user, they are allowed; a reference belonging to another user is a conflict. A `billing_phone`, order recipient phone, or unverified contact detail is not automatically a login or OTP ownership claim.

The production canonicalization is **not approved**. For the first isolated experiment only, keys are fixed, synthetic ASCII values and exact binary equality. The experiment must explicitly demonstrate that it does *not* cover real WP collations, Unicode, equivalent email forms, Persian/Arabic numerals, Iranian country prefixes or phone normalization. Production must first choose one versioned mapping, demonstrate consistency with all supported WP/DB lookup comparisons and test each equivalent and distinct form. It must either reconcile or block unsupported existing and new values; silently treating equivalent mobile forms as separate accounts is unacceptable. No automatic lowercasing of arbitrary email local parts, phone conversion or account merging is authorized by this design.

The candidate model is one unique claim `(scope, equality_version, key) -> owner_id` and separate source references per source row/field. Transactions and locks must ensure that adding the same owner's second reference is permitted, a different owner is rejected atomically, removing one reference never frees a still-used claim, and simultaneous change/delete cannot release or transfer the wrong owner. Hashes of emails or phone numbers are still potentially identifiable: apply access control, retention and redaction; never put claims, raw credentials, or exception SQL into logs or the repository. Prototype datasets are synthetic only.

## 4. Mutation, account creation and failure semantics

1. Enforce the `021A` method/origin/TLS/header guard **before** policy checks, identity lookup or account creation. Honor relevant site and WooCommerce registration options and WordPress validation/filter outcomes for whichever flows are actually supported; failure yields no cookie or access token.
2. Database enforcement must cover source table INSERT, UPDATE and DELETE and relevant `cb_mobile` meta operations for all configured writers, including duplicate meta rows, source reassignments, missing/invalid user, rollback, deadlock and crash recovery. User login and email arriving on the same row must allow equal values for the same owner. Any prohibited/conflicting write must not commit a conflicting source row; a later verification read is not a substitute.
3. `wp_insert_user` may perform multiple writes and fire PHP hooks or email/other external actions. Unless a specific flow's entire behavior has been tested, do not promise that wrapping it in a transaction rolls those side effects back. If an account is created but metadata or session creation fails, retain the account, return a truthful partial-failure state with no token/cookie, and provide a safe recovery path. No automatic user deletion, guessing, privileged role grant or automatic association with another user.
4. Password login, OTP creation, reset, mobile API, WordPress admin, WooCommerce forms/checkout and user changes require separate end-to-end tests before a claim that they are supported. The current OTP transient's check/delete is not atomic; B02 does not solve OTP replay or prove ownership. Refresh/password fingerprint guarantees from `021A` remain necessary independently.

## 5. Migration, activation, rollback and review gates

Before considering any real installation: choose and test canonicalization and all source-table DML paths; validate compatible transactional engines, database versions, collations, indexes, trigger semantics, existing triggers, permissions and supported topology; identify all active writers and untrusted bypasses; run a privacy-preserving read-only duplicate/unsupported-value audit with explicit site-owner authorization; and resolve conflicts through a reviewed owner-controlled process. An audit must not export identities or credentials into repository evidence. Backups, verified restore, maintenance/fail-closed handling and explicit release/rollback ownership are required; no real-site migration is authorized by this card.

An activation check must be a **gate**, not an assertion of perpetual safety: request-time trigger/schema checks cannot eliminate a race with privileged DDL or an uncontrolled restore. Production enforcement requires an appropriate independently verifiable deployment control that prevents untrusted bypass for the entire active period, plus a documented response to detected drift. Ordinary shared-hosting, unrestricted plugins, custom DB drop-ins, multisite, replication, unavailable trigger privileges or schema differences remain unsupported until individually proven. If any condition is missing or fails, do not enable the new registration path; do not silently weaken it.

Migration/rollback must be idempotent, interruption-safe and tested against duplicates, concurrent writes, same-owner aliases, backups/restores and the installed database version. Reversal must never erase user data, account ownership or erase claims while writes are still accepted. A separate owner review of a persistent synthetic fixture is required by B04 and a real-site operation would require its own authority. A prototype, successful synthetic migration, trigger-presence check or previous QA does not establish production readiness.

## 6. Prototype decision and limits

Proceed to a **bounded synthetic feasibility experiment**, not a ready registration service: use a disposable MariaDB and actual WordPress core to test whether database-enforced ownership can intercept racing, noncooperative inserts. First isolate exact-match user-row creation; explicitly label UPDATE/DELETE, mobile metadata, normalization, migration, recovery and deployment hardening unimplemented until separate work and tests prove each. The experiment must reproduce the previous race without protection, reject the second owner with protection, permit same-user login/email aliases and exercise concurrent independent users and failure rollback. Never use a preserved site's database, install triggers there, or enable routes.

If these tests show incompatibility or the remaining implementation exceeds M, split or stop; don't convert a partial proof into B DONE. Any existing master checklist, PWA login or manual QA status remains unchanged.
