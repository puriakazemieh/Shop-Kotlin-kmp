# P00-PWA-AUTH-WP-021C04B03C02B — identity and lifecycle reassessment

Date: 2026-10-18. Result: the comparison is complete; **no candidate is demonstrated to meet the full parent contract**. This is a source review and interpretation of the prior synthetic experiments, not an end-to-end security test and not a production change.

## Observed code paths

- The isolated browser password primitive ([source](../../../wordpress/carmilla-bridge/includes/class-cb-web-auth-login.php)) explicitly registers no route. For an identifier it queries distinct user IDs across login, email and `cb_mobile`, rejects a result other than one, calls `wp_authenticate`, checks the returned ID and then issues a session. Its single lookup uses the DB's collation; it has not established an atomic guarantee against later uncooperative writes between lookup, authentication and issuance. It excludes `billing_phone` from identity. This is not a claim that all deployed login flows use the primitive.
- The existing bridge controller ([source](../../../wordpress/carmilla-bridge/includes/class-cb-auth-controller.php)) declares legacy login, register, OTP and reset routes; its mobile lookup selects at most one `cb_mobile` owner, then falls back to a login. OTP login and reset reuse that lookup. Password login has a separate resolver which also selects at most one metadata match. Its registration checks existing username/email before `wp_insert_user`, then optionally writes `cb_mobile`; those checks are not a concurrency guarantee. OTP registration also creates a user and writes metadata. This source-level observation does not establish that any particular deployed installation has conflicting users, nor does it prove an exploit in that installation.
- The plugin's [route registration](../../../wordpress/carmilla-bridge/includes/class-cb-plugin.php) calls the legacy controller's registration method; manifest/configuration and the active installed version determine actual accessibility. Other WP, WooCommerce, import and plugin writers are not controlled by the new browser helper. Account profile's `billing_phone` write is a contact field, not proof of mobile-login ownership.
- The contract in [B02](../P00-PWA-AUTH-WP-021C04B02/identity-contract.md) requires prevention of cross-namespace duplicate ownership under supported WP/WooCommerce writes and no unsafe association. It forbids silently disabling existing routes and recognizes that external callbacks cannot simply be undone by a SQL rollback.

## Comparison

| Approach | Useful property | Unresolved limitation |
| --- | --- | --- |
| Research trigger-backed shared claims | The tested source-row transactions reject several conflicting writers even when they do not take a Carmilla lock. | The synthetic native `wp_delete_user` failure returned success after partial metadata changes and deletion callbacks; insert/update error reporting also had hook/return issues. It is not safe to enable the prototype on a preserved site. Normalization, backfill, plugins, engines, and deployment are unresolved. |
| Query all owners and fail closed on ambiguity | Can reject an already ambiguous lookup on the specific path that does the check; does not need to modify WP core or database schema. | A check and later write/issuance are not atomic against another writer. It neither prevents concurrent duplicate accounts nor makes legacy routes use the check. It therefore does not satisfy global uniqueness or safe registration alone. |
| Controlled-writer lock or unique Carmilla claim consulted only by our endpoints | Can coordinate *cooperating* writers if designed and tested carefully. | WP admin, WooCommerce, importers, third-party PHP/SQL can bypass it unless coverage is demonstrably complete; post-checks cannot reverse hooks or external effects. It does not meet B02's supported-writer scope as currently stated. |
| Direct-SQL deletion fixture from C02A | On synthetic eligible users it rolls back checked SQL failures and emits a controlled post-commit notification. | It bypasses ordinary WP deletion hooks and other lifecycle behavior, does not provide durable notification delivery, and explicitly excludes posts, other writers and plugins. It is not an implementation suitable for real use. |
| Keep new browser registration disabled pending a verified solution | Avoids claiming that the new path provides an unsafe uniqueness guarantee. | Does not repair or disable the existing legacy endpoints and does not fulfill the desired completed registration feature. |

## Concrete unresolved decision and safe direction

The tested claims model and ordinary WordPress callbacks have conflicting failure semantics: in an injected metadata failure WordPress reports successful deletion despite a partial database operation and fires callbacks; arbitrary callback side effects cannot be undone by a database transaction. No experiment so far establishes an implementation that simultaneously gives the full global invariant, preserves every supported native workflow and provides truthful, reversible external side effects on every error. This is a **demonstrated gap in the tested approaches**, not a proof that all conceivable designs are impossible.

Before changing B02's requirements or implementing a scoped replacement, the product owner needs to decide which failure/compatibility contract is acceptable: preserve native WordPress/plugin workflows and explicitly design detection and recovery for non-reversible deletion failures, or limit supported deletion/writers to a controlled path with explicit compatibility restrictions. Neither option permits unsafe authentication or automatic merging of accounts; either needs separate implementation and tests. Until then retain the current B02 contract and keep the new browser registration disabled. Do not infer authority to change real-site schema, existing mobile routes, WP core or a user's data.

## Minimum future evidence, conditional on a chosen contract

- Real synthetic WP plus independent SQL on the supported version matrix: simultaneous cross-login/email/mobile creation and changes by supported and bypassing writers, duplicate same-owner references, ambiguity, cache and lookup races, and no wrong-user token or OTP binding.
- Native and controlled deletion with deterministic SQL failures, observable hook order/results, posts/reassignment and supported plugin effects as applicable; report externally emitted effects honestly and test recovery rather than asserting rollback undoes them.
- Account-created/session-failed recovery with no token and no destructive cleanup; independently cover OTP atomic consumption and legacy paths before claiming their safety.
- On disposable copies only, test canonicalization, pre-existing conflict audit, compatible schema/engine/permissions, interruption, activation and rollback. A real-site audit or migration still requires its own explicit authorization, backup and owner review. No evidence in this card implies these tests or migrations have already happened.
